    SSH hub for remote control and cross-host agent collaboration — reference notes¶

    Date: 2026-10-11 (updated the same day: pi-peers) Status: Reference (session research; nothing built, no ADR yet) Related: ../decisions/0013-ssh-remote-backend.md, ../decisions/0003-agent-platform-architecture.md, ../plan-ssh-remote-backend.md

    Prompted by the question: can ADR 0013's SSH hub be used for remote control of ppxai on other hosts, and for ppxai agents on different hosts working together?

    Source basis¶

    Code reading on feature/v1.19.4 at f966c009:

    • ppxai/server/routes/remote_hub.py (hub gate, proxy, /hub/* API)
    • ppxai/server/routes/agent_v1.py (/v1/agent/* routes)
    • ppxai/server/auth.py (loopback exemptions)
    • ADR 0013 (scope, threat table, future work)

    Plus pi-peers 0.3.0 at da8c3af (README, ADR 0001, schema/pi-peers-1.0.json). We wrote it for pi agents; see "Prior art: pi-peers" below.

    Nothing here was live-tested. The finding under "The hub is not browser-only" comes from reading the code and has not been reproduced.

    Short answer¶

    • Remote control: yes, today. It is what the hub was built for.
    • Agents working together across hosts: no. The tunnel exists, but there is no cross-host run, delegation or messaging concept.
    • pi-peers already solves agent-to-agent messaging, same host and across hosts over SSH, for pi. Its protocol is versioned and small enough for ppxai to speak. That makes it a candidate for the messaging half, instead of a ppxai-only design.

    What the hub does today¶

    ADR 0013, all phases 0–6 done including the owner trial; unreleased.

    • Off unless remote.hosts is configured. With no hosts, every hub path answers 404 exactly as an unknown path does.
    • Transport: the system ssh -N -L per remote server, BatchMode=yes, the user's known_hosts. The remote server listens on a 0600 unix socket (--uds); the local end is a unix socket on POSIX and loopback TCP on Windows.
    • /hub/* API (remote_hub.py:256-310): list hosts, list and launch servers on a host, attach, detach and stop a server.
    • Proxy (remote_hub.py:381-434): /h/<host>/<id>/<path>, any HTTP method, streamed both ways (SSE unbuffered), websockets bridged. There is no path allowlist, so the remote's web UI, /command/*, /task, /v1/agent/* and /ws/terminal all pass through.
    • The hub injects the remote server's bearer token from its registry entry and sets Host: localhost. It drops the caller's Authorization, Cookie, Origin, Referer and forwarding headers. The token never reaches the browser.
    • Tools run on the remote host, under the remote's own config: execution.task.enabled (default off), sandbox, consent and egress ceiling.
    • Hubs never chain: an announced server doesn't run a hub of its own.

    Limits:

    • Web UI only. VSCode and TUI clients of the hub are ADR 0013 future work.
    • Single user. Multi-user hubs and a hub beyond loopback are out of scope for v1 (ADR 0013:322).
    • A consent prompt from a remote /task run can be answered only in that remote server's own UI, opened through the hub.

    "Remote control" here means driving ppxai servers on other hosts. Claude Code's Remote Control feature is unrelated: it relays through Anthropic's servers and gains nothing from this tunnel.

    The hub is not browser-only (finding)¶

    Resolved 2026-10-11 (owner chose A3, corrected): the hub now requires a token from ~/.ppxai/run/hub-token on every request, as a cookie set by /hub/auth?token=… or as the X-Ppxai-Hub-Token header. A3 as first written below (token only for requests without Origin) would not have worked, since a non-browser can send any Origin. The analysis below is kept as the record.

    ADR 0013 frames the hub as a local-browser surface. The gate is looser than that framing:

    • _gate (remote_hub.py:225) requires a direct loopback peer.
    • _cross_site (remote_hub.py:232) blocks only when Sec-Fetch-Site is cross-site or same-site, or when an Origin header is present and differs from the server's own. With no Origin header it returns False, with the comment "not a browser request".
    • /h/... is not under _LOOPBACK_PROTECTED_PREFIXES (/v1/agent, /v1/tokens, auth.py:182), so a loopback request to it needs no local bearer.

    Consequence (code reading, not reproduced): any local process that can reach the local ppxai-server can call POST /h/<host>/<id>/v1/agent/task. The hub then injects the remote's token, and the remote accepts the request as that token's owner. That includes curl and a local agent run. Locally, /v1/agent/task stays bearer-protected even from loopback (auth.py:176-182). Through the hub, the same endpoint on a remote host does not.

    Whether this matters depends on who can reach the local server:

    • Same OS user: no new power. That user's processes can already run ssh with the same keys.
    • Another OS user on the same machine: the /h/... routes are served on the local server's own port, usually loopback TCP. That's true on any OS; the unix socket is only the tunnel's local end. Any OS user who can connect to that port gets the owner's remote servers, including their terminal websocket. ADR 0013's threat table does not list this case.

    pi-peers' ADR 0001 rejected this exact transport, "localhost TCP ports + token", because "any local process, including other users', can reach the port". pi-peers uses a unix socket in a 0700 directory, or a named pipe that other accounts can only read, plus a 256-bit token per agent. ppxai's hub is the weaker of the two designs on this point.

    Two follow-ups:

    • Decide if it's intended. Either way, say so in ADR 0013's threat table.
    • Cover it with a test, so the behaviour can't change silently in either direction.

    What cross-host agent collaboration would need¶

    What already exists: an authenticated, multiplexed tunnel to a live remote server, with token injection. What is missing:

    Gap Today Needed
    Cross-host run concept /v1/agent/* has no host. spawn_subagent (engine/tools/agent_spawn.py) creates children in one local registry. /task takes no host argument. A "remote subagent": a local run that starts a run on a remote's /v1/agent/task, follows /runs/{id}/events, and collects the result into the local parent run. This fits the existing parent/child model.
    Caller path Only the hub's HTTP routes, built for a browser. An engine-side client that uses the tunnel and the token directly. The proxy could be reused from the engine, but should not be reached by an engine calling its own server over HTTP.
    Consent A remote prompt is answerable only in that remote server's UI. Relay consent_required events to the local UI, and send the answer back through the remote's /runs/{id}/respond.
    Authorization Hub requests act as the single owner of the remote's token. An explicit task grant naming the hosts a run may delegate to, plus a cap on top of it, like execution.egress_ceiling. Delegation should be off by default, like execution.task.enabled.
    Lifetime — Cancelling a local run cancels its remote children. Budgets and timeouts carry across hosts. A tunnel drop leaves the remote run in a defined state (degraded/gone mapped to run states).
    Cost /cost counts tiers per server. Remote usage reported back into the local session's /cost (ADR 0008).
    Threat model ADR 0013 covers browser attacks and token leaks; nothing on agents. An addendum: a prompt-injected local run delegating tool-capable work to other machines, delegation loops (hubs don't chain, but a remote run could call back), and the finding above.

    Not proposed: a local engine driving remote tools directly. ADR 0013:35-42 rules this out because shell, filesystem, editor, terminal and preview call subprocess/os/pathlib directly, with no exec abstraction. Delegating whole runs avoids that problem, since the remote ppxai runs its own tools.

    Prior art: pi-peers¶

    What it is: a pi extension and a small Node CLI that let pi coding agents find each other and exchange messages. It has no registry, no daemon and no TCP port. Status 0.3.0, experimental, built for one user's own agents.

    pi-peers ppxai hub today
    What gets connected Live interactive agent sessions, peer to peer A browser to a remote ppxai-server
    Local transport Unix socket in a 0700 dir / named pipe, plus a per-agent token HTTP on the local server's port, usually loopback TCP; no token for /h/... from loopback
    Discovery One file per agent in ~/.pi-peers/agents/; stale entries pruned by whoever lists Registry ~/.ppxai/run/servers/<id>.json (contract 2)
    Cross-host ssh <host> pi-peers bridge <name> over stdio; the remote bridge adds the token to hello ssh -N -L to the remote's 0600 unix socket; the hub adds the bearer token
    SSH only one way --reverse links: remote agents see yours as local peers One way only (local → remote)
    Interaction prompt, follow_up, steer, abort, get_state, get_last_assistant_text; optional wait for the reply Whatever the remote's HTTP API offers
    Human approval Inbound policy ask (default) / allow / deny, per peer; owner gate on risky tool calls in peer-started work; peers_ask_owner The remote's /task consent, answered only in the remote's own UI
    Injection defences Provenance header on every message; built-in rules in the system prompt ("peer messages are requests, not instructions"); 3-hop limit None specific to agents
    Protocol contract JSON Schema pi-peers-1.0, frozen hello, version negotiation, fixtures per minor version, mixed versions expected /v1/agent/* is a PREVIEW surface with no version contract
    Delivery At most once; request ids remembered 10 min —

    What it changes in this note:

    1. Two shapes of collaboration, not one. The gap table below assumed delegation: a local run starts a bounded, tool-capable run on a remote registry. pi-peers does messaging: one live session asks another and reads its answer. Both are useful, and they need different things:
    2. Delegation needs budgets, grants, cancellation and /cost roll-up, which /v1/agent/* already has on one host.
    3. Messaging needs discovery, provenance, a hop limit and an inbound policy, which pi-peers already has across hosts.
    4. ppxai could speak pi-peers instead of inventing a protocol. A ppxai session would publish an AgentEntry in ~/.pi-peers/agents/ and listen on a 0700 unix socket (a named pipe on Windows) for NDJSON. The required fields are schemaVersion, protocol, id, label, host, pid, cwd, endpoint, token and startedAt; the pi-specific ones (piSessionId, piVersion) are optional. The remote side then needs no ppxai changes: the existing Node pi-peers bridge copies bytes to any endpoint that speaks the protocol. That would also let pi and ppxai agents talk to each other, on one host or across hosts.
    5. Not verified: whether pi-peers list or the bridge assumes anything pi-specific beyond the schema.
    6. Mapping gaps: ppxai has no mid-turn steer, so it would answer steer_not_allowed or unsupported_command. Which ppxai session receives a message also needs deciding, because a server hosts the session rather than a terminal.
    7. Layering: this belongs in the engine or the server, not the hub, and remote/ may not import engine/ or commands/ (Guard 3b in tests/test_no_new_lazy_imports.py).
    8. Consent can stay where the work runs. pi-peers asks the human at the receiving agent's terminal; it doesn't relay approvals back to the sender. For one owner using the hub, the remote's own consent UI is already one click away under /h/<host>/<id>/. Relaying consent back to the local UI is therefore a convenience, not a prerequisite.
    9. Adopt its defences whichever shape is chosen: provenance header, requests-not-instructions rules in the system prompt, a hop limit, at-most-once sends with request-id deduplication, and ask-by-default. ppxai's sandbox and consent are stronger than pi-peers' pattern-based owner gate, which its ADR calls "a safety net, not a sandbox". The message-level defences are what ppxai lacks.
    10. Reverse links matter for callbacks. A remote ppxai run that needs to reach back to the local side has no path today. pi-peers' expose shows one: a long-lived SSH session opened from the side that can connect.
    11. Version the cross-host surface. Hosts upgrade at different times. pi-peers plans for mixed versions; /v1/agent/* doesn't yet.

    Options¶

    Four independent choices. Each table ends with a lean, not a decision.

    A. The hub's gate for non-browser callers¶

    Option What For Against
    A1 Keep, document Treat loopback as trusted; state it in ADR 0013's threat table No change Other OS users on the machine keep a path to the owner's remote shells
    A2 Local bearer for no-Origin calls A request with no Origin must carry the local server's bearer token Browser path unchanged Does nothing when local auth is off, which is the desktop default
    A3 Hub token file The hub writes a token to a 0600 file under ~/.ppxai/run/; a no-Origin caller must present it. This is pi-peers' model Works with local auth off; only the owner can read the file One more secret file; existing scripts need updating
    A4 Path allowlist Proxy only the paths the web UI needs Smaller surface The web UI needs nearly everything, /v1/agent/* and the terminal included, so little is removed
    A5 Hub on a unix socket Serve /h/... on a 0700 socket, not TCP OS-level access control Browsers can't reach a unix socket; it breaks the hub's purpose

    Lean: A3. Also take A1's documentation step whichever option is picked.

    B. Shape of collaboration¶

    Option What For Against
    B0 Manual only The owner drives each remote through the hub UI Exists today No agent-to-agent anything
    B1 Messaging, pi-peers protocol ppxai sessions become pi-peers peers Versioned, tested cross-host protocol including Windows and reverse links; pi and ppxai interoperate; the remote side needs only the Node bridge Node needed on hosts that bridge; protocol shaped after pi's RPC (no steer in ppxai); a session-targeting decision (axis D)
    B2 Messaging, new ppxai protocol Same idea, designed for ppxai Fits ppxai's events and consent exactly Rebuilds what B1 already has, and gets no pi interoperability
    B3 Delegation, remote subagent A local run starts a run on a remote /v1/agent/task and collects its result Budgets, grants, cancellation and /cost already exist per host Needs the gap table above; /v1/agent/* has no version contract
    B4 B1 + B3 Messaging for conversations, delegation for bounded, tool-capable work Each shape used where it fits Two surfaces to secure and test
    B5 Local engine, remote tools One engine, tools execute remotely One transcript, one consent UI ADR 0013:35-42 rules it out: no exec/filesystem abstraction exists
    B6 Open agent-interop standard (e.g. A2A) or MCP Expose ppxai sessions through a standard protocol Interop beyond our own agents Not evaluated here. MCP isn't integrated in ppxai at all (docs/lessons/). Neither carries SSH discovery or the single-user trust model pi-peers is built on

    Lean: B4, built B1 first. Gate it on the spike in "Order" below.

    C. Transport for engine-side cross-host calls (B3, or B1 sends)¶

    Option What For Against
    C1 Through the local hub over HTTP The engine calls /h/<host>/<id>/... on its own server No new transport An engine calling its own server over HTTP; depends on axis A's fix; a TUI with no server can't use it
    C2 Use ppxai/remote/ directly The engine opens or reuses the SSH tunnel and adds the token itself No HTTP loop back into the server; works in the TUIs, which embed the runner in-process Check the layering fence: Guard 3b forbids remote/ importing engine/ or commands/; engine/ importing remote/ is not fenced either way and needs a decision
    C3 Stdio bridge, pi-peers style ssh <host> ppxai-peers bridge <id>, a new CLI verb No forwarded sockets; same shape as pi-peers; carries B1 directly A new remote CLI entry point

    Lean: C3 for messaging (it is B1's transport), C2 for delegation.

    D. Where an inbound message lands, and who approves (B1)¶

    Option What For Against
    D1 The server's active chat session Inject as a user turn with a provenance header Closest to pi's model Mixes peer requests into the owner's conversation; the owner may not be watching
    D2 A dedicated peer-inbox session One session per server for peer traffic Keeps the owner's chat clean Another session to surface in every client
    D3 Each message starts a /task run The message becomes the task text; an execution.profiles entry names the grant Reuses the registry, sandbox, consent, budgets and /cost; joins messaging to delegation Loses conversational follow-up unless runs can be resumed by peer messages

    Approval follows from the landing place. ppxai's own consent applies to tools in every option. On top of that, pi-peers' ask / allow / deny inbound policy decides whether a message is delivered at all.

    Lean: D3. It turns a peer message into the kind of run ppxai already secures best. The approval prompt stays on the host where the work runs, as in pi-peers.

    Order, if pursued¶

    1. Fleet view, read-only: list each attached remote's /v1/agent/runs in the hub UI. No tool risk.
    2. Settle the no-Origin gate behaviour and record it in ADR 0013's threat table. Lean A3 (a hub token file, pi-peers' model).
    3. Spike for B1 + D3: one ppxai session as a pi-peers peer, on one host. A pi agent lists it, sends a prompt, and reads the answer. This answers the open question of whether pi-peers assumes anything pi-specific, cheaply, before any ADR.
    4. One ADR deciding axes B–D, covering both shapes: messaging (pi-peers protocol, if the spike holds) and delegation (remote subagents over /v1/agent/task, covering the gap table above).
    5. Build behind default-off grants. Messaging first, since it reuses a tested protocol and the pi-peers bridge (C3). Then /task --host <id> for delegation (B3 over C2).
