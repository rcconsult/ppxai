Lifecycle of a /v1/agent/task run

A tool-capable run executes in the background, decoupled from any UI. That decoupling is the whole design — and it forces two special mechanisms: /respond to feed a decision to a run that's paused mid-flight, and /ack to collect the result of a run that has already finished and exited.

Mid-run · process alive

POST /v1/agent/runs/{id}/respond

A background run can't pop a dialog. When it needs a human — a consent gate for an action outside its granted envelope, or a branching decision — it enters waiting, emits AGENT_WAITING tagged with the run_id, and idles on a resume token + TTL. The process stays alive.

A run killed while parked drops its stale consent card on the client; /task resume rebuilds the runner from the persisted run meta rather than replaying the dead card.

→ /respond hands back the answer and the run continues.

End-of-run · process dead

POST /v1/agent/runs/{id}/ack

On success the agent writes results, emits AGENT_RESULT_READY, and exits — freeing tokens/CPU and tearing down the sandbox. The run holds in completed_pending_ack so a disconnected UI can still collect the result. A retention TTL is the backstop.

→ /ack confirms collection → finalized → GC-eligible.
