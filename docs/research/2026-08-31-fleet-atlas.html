The hierarchy: config → class → wire

today + designed

Ten configured provider entries funnel into four Python provider classes, which speak three wire protocols. The mapping is not one-to-one in either direction — that asymmetry is the whole subject of ADR 0012. OpenAI already splits per model across two wires, and Perplexity is about to be forced to.

The four wire protocols

3 live, all three now handlers (ADR 0012 W4) · 1 designed

chat_completions

POST /chat/completions · OpenAI SDK

The workhorse: 8 of 10 config entries end here. Tool calls go out as a tools array and come back as tool_calls; results return as tool-role messages.

  • Message conversion: wire.ChatCompletionsHandler (ADR 0012 W4; BaseProvider._convert_messages now delegates to it)
  • ADR 0006's validator guards all three wires since W4 — it guarded only this one until then (Item 62, closed)
  • Perplexity's copy of it retires 2026-09-27

responses

POST /v1/responses · OpenAI SDK

Server-side conversation state (previous_response_id), tool calls as function_call items. Live for OpenAI codex/pro models — and measured live on Perplexity: the stock SDK drives its Agent API unchanged.

  • Implemented once: openai_native.py · _chat_responses_api
  • Routing today: hardcoded prefix tuple, not the profile table (Item 61)
  • I4b re-registers it on PerplexityProvider

generate_content

google-genai SDK

Gemini's native wire: parts arrays, user/model roles, system prompts hoisted to system_instruction. No tool-call ids — pairing is by function name.

  • Its incompatible _convert_messages override is deleted (ADR 0012 W4) — conversion lives in wire.GenerateContentHandler and returns its own honest shape (Item 62, closed)
  • Gemini 3.x makes thought_signature mandatory (Item 54)
  • Falls back to chat_completions if google-genai is absent

messages designed

POST /v1/messages · anthropic SDK

Anthropic-native: top-level system, required max_tokens, tool calls as tool_use blocks, results batched into a single user message.

  • Specified in ADR 0012 §6; built with feat/anthropic-provider
  • thinking blocks must round-trip unchanged (Item 45's bug class)
  • Separate provider = separate billing/token (§7, owner decision)

Declared vs routed: the api_path drift

debt Item 61 · measured 2026-08-30 · RESOLVED in W2

The profile table carried an api_path per model — merged through the config precedence ladder, operator-overridable, displayed by /provider — and nothing routed on it. The actual router was a hardcoded prefix tuple. The two disagreed on three models, in both directions, and an operator's override was silently inert.

Resolved 2026-08-30 (ADR 0012 W2). Routing now reads get_facts_for_model(model).wire_protocol through one reader, consumed by all four dispatch sites. The prefix tuple survives only as seed data. Each row below was resolved as a decision, not by copying one side onto the other — the "resolved to" column names the winner and why.

"gpt-5.3-codex" missed the tuple because "codex" is a prefix match, not a substring. Two fences now hold the line (tests/test_wire_responses_extraction.py): declared-vs-routed agreement across every built-in profile, and an operator override proven to change the outgoing request in both directions — asserted at the client spy, not at the resolver, because resolving correctly is exactly what the inert field also did.

Every row now rests on an observed response. gpt-5.5-pro was the one exception — filed by analogy, because nothing had ever routed it to Chat Completions and so no 404 had ever been seen for it. Probed 2026-08-31: it answers 404 "This is not a chat model and thus not supported in the v1/chat/completions endpoint", the same error verbatim that put its siblings on the list. The assumption was marked as an assumption while it was one, and the measurement confirmed it.

Perplexity Agent API

the same perplexity entry, second wire (ADR 0012 §5 · W3) responses SHIPPED 2026-08-31 chat wire retires 2026-09-27

Live since ADR 0012 W3 (2026-08-31). Routed as table data — anthropic/* · openai/* · google/* · xai/* · perplexity/* resolve wire_protocol="responses" on the one perplexity provider; no code branch names a vendor. Canary verified end to end: anthropic/claude-sonnet-5 emitted a native function_call for read_file(path="/etc/hostname") with a real toolu_bdrk_… id.

One model, two wires, two capabilities — measured. perplexity/sonar on the Responses wire accepted a tools array and called the tool; bare sonar answers 400 "Tool calling is not supported for this model" on Chat Completions. That is the sharpest evidence anywhere in this atlas for why capability cannot be a property of a provider.
