ppxai agent platform · design proposal

A /task command family that mirrors the run lifecycle

One verb per state transition. Every change to a run is reachable three ways that hit the same endpoint — a /task sub-command, a control in the run pane, and (for automation) the raw POST. Tool-free work stays on /run; /task is the tool-capable, sandboxed tier.

> /task "triage the failing CI job" --tools read_file,grep,fetch_url --allow api.github.com --budget iters=20,time=300
  ⟳ r_7fq2  pending → running   gpt-5.4-mini · read_file grep fetch_url · ↗ api.github.com

> /task ls
  ● r_7fq2  running            triage the failing CI job        0:41
  ⏸ r_5kd8  waiting · consent  migrate the config loader        needs approval
  ✓ r_2ab1  pending-ack        summarize the release notes      collect ↵

> /task respond r_5kd8 approve
  ▸ r_5kd8  waiting → running   approved: write_file ./config.py

> /task collect r_2ab1
  ✓ r_2ab1  completed_pending_ack → finalized   result collected
Status today: the /task command family is built and live in web + VSCode as of v1.19.0 (T1–T8a) — direct launch plus ls, get, watch, cancel, respond, collect and resume all ship, backed by the full waiting / completed_pending_ack / finalized lifecycle. The TUI port (T8b) is parked pending a transport decision; the container tier (T9) stays deferred.

03 Launch flags & guardrails

Flags on /task map 1:1 to the request body.

  • --tools a,b,c — capability grant (required; a tool-free run belongs on /run). Include spawn_subagent to permit one child.
  • --allow host[/path],… → network.allow_outbound. Empty = no egress (fail-closed).
  • --provider / --model — per-run intent; default from execution.default_subagent.
  • --budget iters=,time=,tokens= → BudgetSpec (cooperative caps at loop boundaries).
  • --work-dir <path> — working directory for the run's relative tool paths (default: the session's working dir; sealed runs keep their jail and warn).
  • --persona <name> / --system "…" — agent-spec / system framing layered on the bounded-agent default.

The tier's existing guardrails stay authoritative — the command just surfaces them.

  • Default-off. execution.task.enabled=false → run returns 403 with the enable hint; the tool-free tier stays available.
  • No shell grant. --tools …,execute_shell_command → 400 (escapes the egress allowlist; needs tier-d).
  • Auth required — even on loopback. /task is never loopback-exempt; the local client needs a token. /run keeps the exemption only while execution.run.web_search is off — once the config grants web_search the endpoint is a capability and requires a bearer even from localhost.
  • Owner-scoped. a run is readable/cancellable only by its owner; ls/show scope to you.
  • Depth = 1, N = 1. a child can't spawn; a parent drives one child at a time.

05 Spec & skill files

A file carries two separable things: instructions (prose → the run's system) and configuration (grant · provider · budget · egress · read-scope → the request fields). One task-spec concept, several serializations. A spec can only request capability — the operator's policy is the ceiling (§9, "inject intent, default-deny capability").

Precedence (highest wins): CLI flags → --spec file → --skill front-matter(s) → server default_subagent — then clamped by the operator ceiling (allowed grant · no-shell · execution.task.enabled). Delivery: local operators pass a path (server reads it); remote/web clients read + inline the spec and upload skill references.

06 Filesystem sandbox config execution.task.sandbox

A new config block seals where a task may read and write. The scoping fields are tier-agnostic; enforcement selects how they're realized — a soft in-process path-jail today, real container mounts under the container tier. The same config graduates from soft to hard by flipping one field.

"execution": { "task": {
  "enabled": false,
  "sandbox": {
    "enforcement": "in_process",          // "in_process" | "container"

    "workdir": {                       // the ONLY writable location — a per-task chroot
      "root": "~/.ppxai/runs",          // each run gets root/{run_id}/work
      "writable": true,               // write_file/apply_patch confined here
      "cleanup": "on_finalize"          // "on_finalize" | "keep" | "ttl:24h"
    },
    "read_paths": {                    // read_file/grep/list_directory reach ONLY these
      "allow": ["~/.ppxai/skills", "~/.ppxai/specs"],
      "deny":  ["**/.env", "**/.ssh/**", "**/secrets/**"],  // deny wins
      "follow_symlinks": false        // resolve target, re-check inside allow
    },
    "skills_dir": "~/.ppxai/skills",   // --skill <name> resolves HERE (name, not a path)
    "specs_dir":  "~/.ppxai/specs",
    "allow_skill_scripts": false,     // inert until enforcement="container"

    "container": {                     // used when enforcement="container" (tier-d)
      "image": "ppxai/agent-runner:1.19",
      "read_only_root_fs": true,
      "workdir_mount": "/work",          // pod emptyDir == the writable workdir
      "config_maps": [                 // operator-managed, mounted READ-ONLY
        { "name": "ppxai-skills", "mountPath": "/skills", "readOnly": true },
        { "name": "ppxai-specs",  "mountPath": "/specs",  "readOnly": true }
      ],
      "network_policy": "ppxai-agent-egress",  // k8s NetworkPolicy realizes AC-2
      "resources": { "cpu": "500m", "memory": "512Mi" }
    }
  }
} }

now enforcement: in_process

  • Python path-jail in ScopedToolManager: every read_file/grep/write_file path is resolved and checked against read_paths / workdir before the real tool runs.
  • Per-run workdir is the only writable root — a logical chroot (../ and absolute escapes denied).
  • --skill/--spec resolve by name under the configured roots — a caller can't point at an arbitrary path.
  • Best-effort, matching the trusted-operator preview (threat model A) — operator hygiene, not a boundary against hostile task text.

tier-d enforcement: container

  • The same fields become real OS boundaries: read-only root fs; workdir = the pod's writable emptyDir mount.
  • Skills & specs = ConfigMaps injected into the pod and mounted read-only — the operator seals what a task sees without rebuilding the image.
  • Egress becomes a k8s NetworkPolicy (realizes the same AC-2 allowlist as the in-process NetworkPolicy).
  • The hard boundary that lets a task take untrusted input and permits allow_skill_scripts.
Ship the keys with the enforcer, never before. Parsed-but-unenforced scoping is worse than none — an operator sets read_paths and assumes confinement that isn't there. So execution.task.sandbox lands together with the in-process path-jail; the container block lands with tier-d. Until then this is a design contract, not live config.
