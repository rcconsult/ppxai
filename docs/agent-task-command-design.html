ppxai agent platform · design proposal

A /task command family that mirrors the run lifecycle

One verb per state transition. Every change to a run is reachable three ways that hit the same endpoint — a /task sub-command, a control in the run pane, and (for automation) the raw POST. Tool-free work stays on /agentrun; /task is the tool-capable, sandboxed tier.

> /task run "triage the failing CI job" --tools read_file,grep,fetch_url --allow api.github.com --budget iters=20,time=300
  ⟳ r_7fq2  pending → running   gpt-5.4-mini · read_file grep fetch_url · ↗ api.github.com

> /task ls
  ● r_7fq2  running            triage the failing CI job        0:41
  ⏸ r_5kd8  waiting · consent  migrate the config loader        needs approval
  ✓ r_2ab1  pending-ack        summarize the release notes      collect ↵

> /task respond r_5kd8 approve
  ▸ r_5kd8  waiting → running   approved: write_file ./config.py

> /task ack r_2ab1
  ✓ r_2ab1  completed_pending_ack → finalized   result collected
Status today: no /task command exists in any client — /agentrun (tool-free) is the only agent slash command shipped. This is the proposed surface. The launch, list, show, watch and cancel endpoints already exist; respond, ack and resume are designed (ADR 0003 §8) and need building.

03 Launch flags & guardrails

Flags on /task run map 1:1 to the request body.

  • --tools a,b,c — capability grant (required; a tool-free run belongs on /agentrun). Include spawn_subagent to permit one child.
  • --allow host[/path],… → network.allow_outbound. Empty = no egress (fail-closed).
  • --provider / --model — per-run intent; default from tools.agent.default_subagent.
  • --budget iters=,time=,tokens= → BudgetSpec (cooperative caps at loop boundaries).
  • --persona <name> / --system "…" — agent-spec / system framing layered on the bounded-agent default.

The tier's existing guardrails stay authoritative — the command just surfaces them.

  • Default-off. task_tier_enabled=false → run returns 403 with the enable hint; the tool-free tier stays available.
  • No shell grant. --tools …,execute_shell_command → 400 (escapes the egress allowlist; needs tier-d).
  • Auth required — even on loopback. Unlike /agentrun, /task is not loopback-exempt; the local client needs a token.
  • Owner-scoped. a run is readable/cancellable only by its owner; ls/show scope to you.
  • Depth = 1, N = 1. a child can't spawn; a parent drives one child at a time.

04 What to build

The launch/observe/cancel spine already exists server-side. The delta is the interactive-transition endpoints and the client command family + pane.

have already shipped

  • POST /v1/agent/task — sandboxed run (ScopedToolManager · NetworkPolicy · budgets · spawn N=1)
  • GET /runs, GET /runs/{id}, GET /runs/{id}/events, POST /runs/{id}/cancel
  • Owner-scoped authz; default-off gate; no-shell rejection
  • Web right-panel + AgentRunView pane (from the /agentrun tier — reusable)

build the delta

  • Endpoints: POST …/respond, …/ack, …/resume + the waiting / completed_pending_ack / finalized statuses and AGENT_WAITING / AGENT_RESULT_READY events
  • Client: TaskController (mirror of agent-run-controller.js) + TaskRunView — the denser pane with per-state controls
  • Dispatch: register /task + sub-verbs in command-dispatcher.js; flag parser for the launch line
  • Persona: the agent-spec artifact behind --persona (shared with ppxai-sre)
  • Then: port the family to TUI + VSCode (web first)
